# DECISIONS.md — Finance PSU Learning Platform

## D1 — Which technology stack document is authoritative

**Context:** Three technical-stack documents exist in the client's Google Drive:
1. `technical_stack_specification.pdf` — Python 3.12/Django 5.2 LTS, PostgreSQL 18, Oracle Cloud Always-Free VM, Docker, django-allauth, Cloudflare R2, PDF.js+boto3, Razorpay, Brevo, GitHub Actions backups. Located **inside** the "Finance psu guide" project folder, alongside the invoice and workflow doc. Modified 2026-09-12 (most recent of the three).
2. "Finance PSU Platform Architecture Plan" — Node.js/Fastify, PostgreSQL 16 + PgBouncer, Valkey 8.1, Hetzner CPX32 VPS. Located outside the project folder. States total dev fee ₹24,000, which does **not** match the invoice's ₹25,000.
3. "Vasu CMA - Technical Architecture Blueprint" — Next.js 15+ on Vercel/Cloudflare Pages, Neon serverless Postgres, Drizzle ORM, Better Auth, pg-boss. Located outside the project folder. Implies recurring hosting cost (e.g. Vercel Pro), which conflicts with both other documents' ₹0-base-cost framing.

**Decision:** Use **document 1** (`technical_stack_specification.pdf`) as the sole approved stack. Confirmed directly by the client in this session.

**Rationale surfaced to the client before the decision:**
- It's the only one physically filed inside the project folder with the invoice and workflow doc.
- It's the most recently modified.
- Its ₹0 base-cost framing is internally consistent (no conflicting recurring-fee stack).
- The invoice's frontend requirement — "Bootstrap and lightweight JavaScript" — matches a server-rendered Django app far better than a Next.js/React SPA (doc 3) or an unspecified Fastify frontend (doc 2).

**Consequence:** Documents 2 and 3 are treated as rejected drafts/explorations, not requirements. Nothing from them was carried into REQUIREMENTS.md, ARCHITECTURE.md, or DATA_MODEL.md, except as this decision record and the out-of-scope note in REQUIREMENTS.md §5 (forensic watermarking, which appeared in doc 2/3-style thinking but not in doc 1 or the invoice).

## D3 — Single active session enforced via PostgreSQL, not Redis/Valkey

**Context:** REQ-ACC-02 requires one active login session per account. The rejected Fastify stack draft used Valkey (Redis-compatible) for this; the approved Django stack has no in-memory store at all.

**Decision:** Implement via request middleware backed by PostgreSQL (ARCHITECTURE.md §3.2), rather than introducing Redis/Valkey solely for this feature.

**Rationale:** Adding an entirely new infrastructure component (and its own container, memory budget, and failure mode) to satisfy one feature contradicts the approved stack's own stated goal — "avoiding distributed microservice complexity" and staying on a ₹0 base-cost footprint. Postgres already holds session state via Django's session framework; extending it is the smaller change.

**Update (REQUIREMENTS.md §7 item 3, client-frozen):** the client's own resolution puts the tracked session key directly on a `UserProfile` model (`active_session_key`) rather than the standalone `ActiveSession` table this decision originally proposed — same PostgreSQL-only mechanism, simpler shape. DATA_MODEL.md and ARCHITECTURE.md §3.2 now reflect `UserProfile`, not `ActiveSession`. The exact conflict-handling behavior (`session.flush()` + `logout()` + redirect to `/login/?error=session_conflict`) is also now frozen — see REQ-ACC-03.

## D4 — Autosave is server-synced, not client-only

**Context:** The invoice says "autosave" without specifying mechanism. The rejected Next.js stack draft assumed pure client-side `localStorage` autosave with only the final submission hitting the server.

**Decision:** REQ-MOCK-04 requires periodic server-side persistence of in-progress answers (API.md `/autosave/` endpoint), not `localStorage`-only.

**Rationale:** A `localStorage`-only design loses all progress if the student switches devices/browsers or clears storage — which directly undermines the stated purpose of autosave ("preserve progress"). It's the only reading of "autosave" consistent with the feature's evident intent.

**Resolution source (out-of-folder, disclosed):** The rejected "Vasu CMA" Next.js draft (not in the approved project folder) explicitly took the opposite approach — client-only `localStorage`, synced to the server only on final submit. Having that alternative in hand, read in full, sharpens rather than weakens this decision: that approach was rejected specifically because it's the weaker design for the stated goal (progress must survive a device switch), not because the source was unclear on what "autosave" should do.

**Status:** Resolved as final default — no longer contingent on client confirmation. REQUIREMENTS.md updated to drop this from the open-questions list.

## D5 — Origin web server: Nginx + Gunicorn, Cloudflare Full (Strict)

**Context:** `technical_stack_specification.pdf` (approved, in-folder) jumps from "Cloudflare WAF/CDN" directly to the Django/Gunicorn container without naming an origin-side reverse proxy or describing the Cloudflare↔origin TLS mode.

**Decision:** Nginx + Gunicorn behind Cloudflare Full (Strict) with a Cloudflare Origin CA certificate on the VM.

**Resolution source (out-of-folder, disclosed):** The rejected "Finance PSU Platform Architecture Plan" doc (Fastify/Node stack, not in the approved project folder) independently arrived at the identical origin topology for the same 10,000-user target — its architecture diagram shows Cloudflare doing edge TLS 1.3 termination, then an explicit "NGINX HIGH-PERFORMANCE REVERSE PROXY" on the origin VM with "SSL Strict Snippets" (i.e. Cloudflare Full-Strict with an origin cert), in front of the app process. That diagram is app-framework-agnostic — it describes the edge/proxy/app layering, not anything specific to Fastify — so it transfers cleanly to the approved Django/Gunicorn stack. Two independent architecture passes landing on the same topology is enough signal to stop treating this as an open question.

**Status:** Resolved and adopted as final. ARCHITECTURE.md and DEPLOYMENT.md updated accordingly; recorded in REQUIREMENTS.md §6 (Resolved Since First Draft), removed from the §7 open-questions list.

## D6 — Django admin as the default admin/authoring interface

**Context:** REQ-MOCK-03 requires admin controls for questions/tests/content/access; REQ-WEB-05 requires a blog. No custom admin UI or CMS was specified anywhere.

**Decision:** Use Django's built-in admin site for both, rather than building a custom admin dashboard or integrating a CMS.

**Rationale:** Builds nothing beyond what's requested (CLAUDE.md "Simplicity First"), fits the 14-day window, and is standard practice for a Django app of this scope. Confirmed by direct client freeze (REQUIREMENTS.md §7 item 4) — no longer an open assumption.

## D7 — Load-test target numbers proposed as a default, then retracted

**Context:** No source document — approved or otherwise — states numeric pass/fail thresholds for the load test called for in REQ-OPS-04. Leaving this fully blank made the requirement untestable.

**Decision:** Adopt the following as a *proposed default* target, not yet client-signed-off, added to TESTING.md §3:
- Cloudflare-cached public pages (homepage, catalog, blog): p95 response < 100ms at the edge, 0% origin load.
- Authenticated dynamic requests (dashboard, session check, entitlement check): p95 < 300ms at the origin, error rate < 1%.
- Payment webhook processing: 0 dropped/timed-out webhooks under load (money-correctness takes priority over latency here).
- Overall: system remains responsive (no 5xx cascade, no DB connection-pool exhaustion) through a simulated ~90/10 split — roughly 9,000 of 10,000 simulated users on cached catalog/browsing traffic, the remainder on authenticated dashboard/PDF/mock-test actions — reflecting the actual described usage pattern (most traffic is browsing, not concurrent test-taking).

**Resolution source (out-of-folder, disclosed):** These targets are adapted from the rejected "Vasu CMA" Next.js draft's traffic-tier breakdown (its own tier-specific numbers — e.g. "<50ms edge", "<2ms indexed session lookup" — were written for a serverless/Neon stack and are not directly portable, so the numbers above are deliberately loosened/adapted for a single-VM Django/Gunicorn/Postgres deployment rather than copied). The *shape* of the analysis (most load is cache-absorbed browsing, not authenticated write traffic) is framework-agnostic and matches how the approved stack doc itself frames Cloudflare's role.

**Status: RETRACTED.** The client explicitly rejected this — instructed to "strip out all invented performance targets like the 90/10 split and Lighthouse numeric limits" and to use only the invoice's own rule instead: capacity must be verified through simulated load testing before scale launch, with no prescribed numeric target. Every reference to these target numbers (TESTING.md §3, ARCHITECTURE.md §5, DEPLOYMENT.md §8, REQUIREMENTS.md REQ-OPS-04/REQ-WEB-06/§6/§7) has been removed or rewritten to state that no numeric target is asserted, only the invoice's own verify-via-load-test language. This entry is kept, not deleted, so the reasoning that produced the (rejected) proposal and the client's correction both stay traceable. The load-test *timing* question this was originally bundled with was separately resolved — see §7 item 6 in REQUIREMENTS.md.

## D9 — Architectural correction pass (client-mandated, this session)

**Context:** After the §7 freeze (D1–D8), the client issued eight direct corrections to close gaps and fix inaccuracies the assistant-authored defaults had introduced. All are implemented as final, not proposals.

1. **Dashboard progress tracking was unmodeled.** REQ-DASH-01 needed "course progress %" and "completed topic count" but no entity computed them. Added `UserChapterProgress` (`user`, `chapter`, `is_completed`) to DATA_MODEL.md; flips to `True` when a student's chapter signed-URL request succeeds (API.md).
2. **`DATABASE_URL`/`dj_database_url` was inconsistent with the rest of the doc set** — `.env` already listed five discrete `DB_*` variables, but the Python snippet read a `DATABASE_URL` that was never actually defined anywhere. Fixed: `DATABASES` is now built directly from `DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT`, keeping `CONN_MAX_AGE=0` and `OPTIONS.connect_timeout=15` (DEPLOYMENT.md §3).
3. **PDF protection was incomplete.** REQ-COURSE-03 and SECURITY.md §5 covered download-blocking but not print or text-copy — both now explicit: a `beforeprint` handler blocks printing, and the PDF.js text layer's selection/copy is unbound. **[Print-blocking superseded by D15 below — printing is now intentionally permitted; this entry's text-copy and download-blocking content is unaffected and still stands.]**
4. **Backup design implicitly required Postgres to be network-reachable from GitHub's runners**, which the client rejected. Redesigned: GitHub Actions SSHes into the OCI host and triggers a host-local `docker compose exec db pg_dump`, encrypted and uploaded to R2 entirely from inside the VM — port 5432 is never published. This also *shrinks* the GitHub Actions secrets surface (SSH creds only; R2/passphrase stay host-side) — see SECURITY.md §2.
5. **Nginx provisioning read as a host-level package install.** Corrected: Nginx is exclusively the `proxy` service inside `docker-compose.prod.yml`; the host installs nothing but Docker/Compose (DEPLOYMENT.md §1–2).
6. **Webhook handling had no explicit duplicate-delivery guard**, even though `Order.razorpay_payment_id` already existed as a field. Made the uniqueness explicit (unique DB constraint) and specified idempotent handler behavior: an already-`verified` `razorpay_payment_id` short-circuits to a 200 with no further writes (API.md §2, DATA_MODEL.md `Order`, SECURITY.md §4).
7. **ARCHITECTURE.md §4 previously implied all state lived on R2**, conflating object storage (PDFs) with the live database. Corrected: the Postgres volume on the OCI VM *is* the live data; R2 only holds off-host encrypted daily backup snapshots. The VM is therefore not freely disposable the way that phrasing suggested.
8. **Numeric performance targets (D7) were an assistant invention the client didn't ask for and explicitly rejected** — retracted per D7 above. The only standard now is the invoice's own language: capacity is verified via simulated load testing before scale launch, no baked-in number.

**Status:** All eight applied across REQUIREMENTS.md, ARCHITECTURE.md, DATA_MODEL.md, API.md, SECURITY.md, DEPLOYMENT.md, and TESTING.md as final (not proposals pending further confirmation) — these are direct client instructions, not assistant defaults.

## D10 — Second architectural correction pass: engineering review of D9's output

**Context:** After D9 shipped, a detailed engineering review of the resulting doc set found fourteen further issues — some outright bugs (a webhook lookup that could never succeed on a first delivery), some unmodeled requirements (course-included mock tests, "recently accessed course" had no data source), some design gaps the D9 pass left underspecified (mock-test deadline enforcement, the backup mechanism's exact shape, admin PDF upload). All fourteen are corrected as final engineering decisions, not proposals — authoritative inputs were REQUIREMENTS.md §7 / D9 itself, the three approved source documents, and engineering judgment only where those don't specify implementation detail. Rejected architecture drafts were not consulted for any of this.

1. **Razorpay webhook lookup key was wrong.** The handler claimed to look up `Order` by `razorpay_payment_id` — but that field is `NULL` until the very webhook that's supposed to set it, so the lookup could never succeed on a first delivery. This supersedes D9 item 6, which correctly identified the need for idempotency but didn't catch this. Fixed: `Order` is created (with `razorpay_order_id` already set) *before* checkout opens; the webhook verifies the signature against the **raw body** first, then looks up by `razorpay_order_id`, processes inside `transaction.atomic()` with the row `select_for_update()`-locked, and validates amount/currency against the immutable server-captured values before ever touching state. Money is now stored as `amount_paise` (integer), never `amount_inr`, removing unit ambiguity at the one place a mistake would be a money bug. See API.md §2, SECURITY.md §4, DATA_MODEL.md `Order`.
2. **`User.is_admin` contradicted "Django's built-in User model."** You can't have both a stock `User` and a custom field on it without a custom `AUTH_USER_MODEL`, which nothing required. Fixed: built-in `User`, unmodified; admin authorization is native `is_staff`/`is_superuser`/permissions. Also made explicit: `ACCOUNT_EMAIL_VERIFICATION = "mandatory"` (django-allauth) — the approved stack doc's "email confirmations" line was previously only ever tested as password-reset, not registration verification. See DATA_MODEL.md `User`, REQ-ACC-01.
3. **Course-included mock tests had no model.** The workflow doc says a purchased course unlocks "Notes / MCQs / Mock Tests," but only standalone `MockTestEnrollment` existed. Added `CourseMockTest` (course↔mock-test join) and one centralized `can_access_mock_test(user, mock_test)` helper — true via standalone enrollment *or* an active course enrollment reaching the test through this join — used by every mock-test route, never re-implemented per view. UX split (standalone → "My Mock Tests", course-included → inside the course) is flagged explicitly as an assumption, not assumed to be a client-frozen merge. New requirement REQ-MOCK-05.
4. **"Recently accessed course" had no data source.** REQ-DASH-01 needed it; nothing tracked access time. Rather than a second tracking table, extended the existing `UserChapterProgress` with `last_accessed_at`, updated on every valid chapter access (not just the first, unlike `is_completed`). "Recently accessed course" = the course of whichever row has the latest `last_accessed_at`.
5. **Mock-test autosave only checked "unsubmitted," not "before deadline."** After the timer visually expires, the old autosave rule would still have accepted answers. Fixed: `deadline = started_at + time_limit_minutes`, computed server-side at request time; every autosave/submit call checks the server's own clock against it first. Past deadline: the answer is rejected and the attempt is lazily auto-finalized on that same request — one documented path, no Celery/Redis/background worker. Submit is now explicitly idempotent (second call returns the stored score, never rescoring).
6. **Backup design depended on an unversioned host script.** D9 already moved backups off a publicly-reachable Postgres and onto SSH+`docker compose exec`, but still relied on a hand-maintained `scripts/backup.sh` living on the host outside any container image. Replaced with a dedicated `backup` Compose service — the backup logic (pg_dump, OpenSSL AES-256/PBKDF2, boto3 upload, cleanup, non-zero exit on failure) lives inside that service's own image. GitHub Actions' entire job shrinks to one command: `docker compose -f docker-compose.prod.yml run --rm backup`. Postgres `5432` stays unpublished either way. See DEPLOYMENT.md §5.
7. **Brevo vs. Razorpay receipt language conflicted.** ARCHITECTURE.md's component table said Brevo sends "payment receipts," while REQUIREMENTS.md §7 item 7 says Razorpay's own receipts are used and no custom GST/invoice system is built. Reconciled without deleting either source requirement: Razorpay sends the actual payment receipt; Brevo sends only signup verification, password reset, and an optional plain purchase-confirmation notice — never called or treated as a receipt/invoice. See SECURITY.md §7, ARCHITECTURE.md §2, API.md §8.
8. **Admin PDF upload mechanism was undefined.** `Chapter.pdf_object_key` existed, but nothing said how an admin actually gets a PDF into R2. Defined: a non-model `FileField` on the Chapter `ModelAdmin` form (not a model-level `FileField`/storage-backed field), server-side upload via `boto3` to a deterministic private object key on save — no public URL ever stored or generated. See API.md §7.
9. **R2 CORS and Cloudflare cache boundaries were never written down**, despite being load-bearing for both PDF.js (needs Range-request CORS) and student data privacy (an edge-cached dashboard/webhook response would leak across students). Documented explicitly: R2 CORS scoped to production origins, GET-only, Range-request headers allowed/exposed; a hard list of routes that must never be edge-cached, with Django sending `Cache-Control: private, no-store` on all of them. See SECURITY.md §9.
10. **Some REQUIREMENTS.md entries overstated their source.** The workflow doc uses "can contain"/"can show" (illustrative) for some course-card and dashboard fields; REQ-WEB-03 and REQ-DASH-01 had tagged the full field lists as flatly `[Confirmed]`, implying the source mandated them. Fixed the *label*, not the *content* — every field the client is retaining stays in the build; the tag now reads "[Resolved implementation baseline — client-retained during planning]" with a provenance note, rather than misattributing a firm mandate to hedged source wording.
11. **Chapter/Topic conflation was true in practice but never stated.** The invoice says "chapter/topic"; the model has only `Chapter`. No `Topic` table was added (nothing asked for a fourth level) — but the mapping is now stated explicitly in DATA_MODEL.md and REQ-COURSE-01, so no one later assumes a separate `Topic` model exists.
12. **The approved stack doc's Django 5.2 LTS maintenance note was never carried into DEPLOYMENT.md.** Added as an explicitly-labeled "Post-Handover Maintenance" section — the April 2028 patch-support horizon and the early-2028 upgrade-planning note, nothing more invented, explicitly not a 14-day-scope item or a handover blocker.
13. **The `Order.item_type`/`item_id` polymorphic design had no DB-level FK integrity**, and was flagged as needing either an explicit acknowledgment or a safer replacement. Chose the replacement: `Order.course_pricing_plan`/`Order.mock_test_pricing_plan`, both nullable FKs, with a DB `CHECK` requiring exactly one set. This one design is now used consistently everywhere `Order`'s target is discussed (DATA_MODEL.md, API.md, SECURITY.md) — the polymorphic approach is fully retired, not left as an alternate description anywhere. A consolidated constraints table now lives in DATA_MODEL.md §3. Stack stays a plain Django/Postgres monolith throughout — no Redis, Celery, microservices, or event bus were introduced by any of the above.
14. **CLAUDE.md had no Finance-PSU-specific guardrails.** Added a short project section (below this decision) capturing the load-bearing rules this whole doc set now depends on, so future work — including actual implementation — doesn't have to rediscover them from `/docs` alone.

**Status:** All fourteen applied across REQUIREMENTS.md, ARCHITECTURE.md, DATA_MODEL.md, API.md, SECURITY.md, DEPLOYMENT.md, TESTING.md, and CLAUDE.md, as final corrections — not proposals. No application code or migrations were written in this pass; DATA_MODEL.md's `Order` redesign, `CourseMockTest`, and `UserChapterProgress.last_accessed_at` are schema *descriptions*, not migrations.

## D11 — Third correction pass: independent Codex freeze audit

**Context:** An independent Codex audit of the frozen doc set (post-D10) found eight substantiated issues — one exploitable payment-verification gap, one concurrency gap in mock-test scoring, one backup design that wasn't actually executable as written, one PDF-loading design at odds with the approved 60-second URL, one privacy leak in the "recently accessed course" derivation, two provenance/wording overclaims, and a cross-reference audit that found several broken section pointers the earlier REQ-ID/D#-only grep passes didn't catch (because the tokens existed, they just pointed at the wrong place) — plus one additional engineering correction (a constraint that was being enforced at the wrong layer). This entry supersedes only the specific D10 details each item touches; it does not rewrite D10's history, and D9/D10's other content stands unchanged.

**D11.1 — Razorpay: exact event AND status, not either.** The webhook handler accepted `status == "captured"` **or** the `payment.captured` event — unsafe, since Razorpay documents that a `payment.authorized` webhook can be delivered while the payment entity's *current* status already reads `"captured"`. Fixed: both conditions required. A non-`payment.captured` event is now explicitly ignored (200, no grant, no retry provoked) before status is even inspected. See API.md §2, SECURITY.md §4, ARCHITECTURE.md §3.3, REQUIREMENTS.md REQ-PAY-02, TESTING.md (new `payment.authorized`-with-captured-status test).

**D11.2 — Mock test: every mutation locks the `Attempt` row first.** The deadline/`submitted_at` checks and the answer writes/scoring were described without a shared transaction + row lock, so two near-simultaneous requests on the same attempt weren't actually guaranteed to serialize. Fixed: `Attempt.objects.select_for_update()` inside `transaction.atomic()`, acquired before checking `submitted_at`, before computing/checking the deadline, before accepting an answer, before auto-finalizing, before scoring — for autosave *and* submit alike. No Celery/Redis/background worker; the lock is a plain Postgres row lock held for one short request. See API.md §5, ARCHITECTURE.md §3.5, DATA_MODEL.md `Attempt`, TESTING.md (three new concurrency tests).

**D11.3 — Backup/restore made actually executable.** Three concrete bugs: the backup command hard-coded `-h db` while `.env` specifies `DB_HOST=psu_data_engine_db` — a mismatch that would simply fail to resolve; the command never exported `PGPASSWORD`, and libpq does not read `DB_PASSWORD` on its own; and the restore path was described as "e.g. `restore.py`" — an unspecified script name, not a real interface. Fixed: the `db` service carries the Compose-network alias `psu_data_engine_db` so `DB_HOST` resolves identically for `web` and `backup`; every command reads `-h "$DB_HOST"`, never a literal `db`; `PGPASSWORD` is exported inside the ephemeral container from `DB_PASSWORD`, never exposed outside it; the backup image owns one versioned entrypoint with exactly two subcommands, `backup` and `restore <r2-object-key>`; the dump format is `pg_dump --format=custom --no-owner --no-acl` consistently, restored with matching `pg_restore` flags into a fresh/empty target by default. See DEPLOYMENT.md §2/§5, SECURITY.md §8.

**D11.4 — PDF loading redesigned around the approved 60-second expiry, not against it.** The prior design implied `Range` requests continuing throughout a reading session — which could break mid-read once the 60-second URL lapsed. Fixed, without extending the expiry, proxying through Django, adding Cloudflare Workers, or building URL rotation: the browser performs **one** complete GET immediately after the signed URL is issued, loads the full response into PDF.js (`getDocument({ data })`), and all further page navigation works off those in-memory bytes — no further R2 requests, so expiry can't interrupt an already-loaded document. A failed initial fetch retries once with one fresh URL. Also corrected an inaccurate claim: the short expiry limits how long a *leaked* URL is usable, it doesn't mean "the URL stops working once viewing starts" — anyone holding it can use it until it expires, same as any presigned URL. R2 CORS simplified accordingly (plain GET, not Range-specific). See API.md §3, ARCHITECTURE.md §3.4, SECURITY.md §9, TESTING.md (Range-request test replaced).

**D11.5 — "Recently accessed course" must come from currently-active access.** The derivation picked the newest `UserChapterProgress.last_accessed_at` without checking whether the underlying course `Enrollment` was still active — so an expired course could surface as "recently accessed" merely because its access history was newest. Fixed: the query now restricts to courses with a currently active (`expires_at__gt=now()`) `Enrollment`; if none qualify, the field is empty/null rather than showing stale expired access. See DATA_MODEL.md `UserChapterProgress`, API.md §3, ARCHITECTURE.md §3.4, REQUIREMENTS.md REQ-DASH-01, TESTING.md (two new tests).

**D11.6 — Provenance overclaims, corrected without changing the selected behavior.** Three instances: (a) mandatory email verification was tagged as though the approved stack doc specified "mandatory" — it only says allauth performs "email confirmations"; the mandatory/blocking mode is an engineering decision, now labeled `[Resolved implementation baseline — production security decision]` rather than misattributed; (b) the ARCHITECTURE.md diagram's Brevo box said "receipts," directly contradicting the client-frozen "Razorpay owns receipts" decision from D10 item 7 — fixed to "purchase confirm(ation), NOT a receipt"; (c) REQUIREMENTS.md described PDF protection scope as invoice-mandated "no download button only" — the invoice only mandates no-download; print/copy stripping comes from the approved stack, not the invoice — REQ-COURSE-03 and the Out-of-Scope note now split that provenance explicitly. No behavior changed in any of the three — only the claimed source of each behavior. See REQUIREMENTS.md REQ-ACC-01/REQ-COURSE-03/§5, SECURITY.md §3, ARCHITECTURE.md diagram + component table.

**D11.7 — Cross-reference audit found broken semantic pointers the REQ-ID/D# grep passes didn't catch.** Grepping for `REQ-*` and `D#` tokens only confirms the *token* resolves somewhere — it doesn't confirm the specific section number/name at the end of the pointer is correct. Found and fixed: API.md §4 and DATA_MODEL.md's `CourseMockTest` both cited "REQUIREMENTS.md §7 item 3" (which is the *Profile* item) for course-included mock tests — corrected to "DECISIONS.md D10 item 3" / REQ-MOCK-05. DATA_MODEL.md's `Chapter` pointed to "§3 'Admin PDF Upload'" — DATA_MODEL.md §3 is Database Constraints and has no such section — corrected to API.md §7. REQUIREMENTS.md §7 items 4 and 7 pointed to "API.md §5–6" and "API.md §6" respectively for Admin and Receipts — those sections are actually API.md §7 and §8 after D10's restructuring — both corrected. REQUIREMENTS.md's own header referenced a section called "Unresolved Questions," a name that no longer exists anywhere in the document (renamed across earlier passes) — corrected to point at NFR-05. ARCHITECTURE.md's component table referenced "§7 receipts note below" ambiguously, which would misread as this file's own (nonexistent) §7 — corrected to name SECURITY.md §7 explicitly. **Going forward, a REQ-ID/D#-token grep is necessary but not sufficient** — a semantic check (open the target, confirm it says what the pointer claims) is required whenever a section gets renumbered or renamed, which the D9/D10 passes' verification steps didn't do thoroughly enough.

**D11.8 — `Question`'s exactly-one-target invariant belongs at the DB layer, not application code.** The prior reasoning ("spans two FK'd tables, needs a trigger") was simply wrong for this specific invariant — `mock_test` and `chapter` are both columns on the same `Question` row, so Postgres can enforce "exactly one set" directly via a `CheckConstraint`, no trigger needed. Fixed: documented as a Django `CheckConstraint` in DATA_MODEL.md, moved out of the constraints table's "application-enforced" bucket into "DB-enforced." The genuinely cross-table invariant (`AttemptAnswer.question.mock_test == Attempt.mock_test`) correctly stays application-enforced — that one really does span two FK-related-but-different rows via a join, which a single-table `CheckConstraint` can't express. ## D13 — django-allauth account settings, against the stock User model

**Context:** D11.6 froze `ACCOUNT_EMAIL_VERIFICATION = "mandatory"` but didn't specify the rest of allauth's account configuration — how a student actually logs in, which signup fields are required, or which allauth settings API (legacy vs. modern) applies to the pinned `django-allauth==65.1.0` in `requirements.txt`.

**Decision:**
```python
ACCOUNT_LOGIN_METHODS = {"username"}
ACCOUNT_SIGNUP_FIELDS = ["username*", "email*", "password1*", "password2*"]
ACCOUNT_EMAIL_VERIFICATION = "mandatory"
```
Stock Django `User` model throughout — no custom `AUTH_USER_MODEL`, no custom login-identifier field.

**Rationale:**
- **No email-only login invented.** No source document specifies how students authenticate — only that signup/login exist and email gets verified. `ACCOUNT_LOGIN_METHODS = {"username"}` keeps allauth's own out-of-box default rather than adding a constraint nobody asked for.
- **Email is still collected and verified** via `ACCOUNT_SIGNUP_FIELDS`'s `"email*"` (required at signup) and the unchanged `ACCOUNT_EMAIL_VERIFICATION = "mandatory"` — verification gates login regardless of which field (`username`) identifies the account.
- **Modern settings, not deprecated ones.** `ACCOUNT_LOGIN_METHODS`/`ACCOUNT_SIGNUP_FIELDS` replace the older `ACCOUNT_AUTHENTICATION_METHOD`/`ACCOUNT_EMAIL_REQUIRED`/`ACCOUNT_USERNAME_REQUIRED` trio, deprecated in allauth 0.63. The pinned `65.1.0` is well past that transition, so the modern API is what's documented — **but that version string is unverified against PyPI** (no live internet access this session); confirm it's real and still on this settings API before relying on it at implementation time.

See SECURITY.md §3 for the full settings block and field-by-field rationale, DEPLOYMENT.md §3 for the `.env`/settings snippet, DATA_MODEL.md `User` for the field list (now includes `username` explicitly, since it's the confirmed login credential).

**Status:** Applied to SECURITY.md, DEPLOYMENT.md, DATA_MODEL.md. Documentation only — no `settings.py` or other application code exists yet; this is the specification to implement against.

## D14 — Google Login added by client after the v1 freeze

**Context:** After `docs-baseline-v1` was tagged, the client explicitly approved adding Google as an additional login/signup method (REQ-ACC-04). This is a genuine post-freeze scope change, not a reinterpretation of anything already frozen — it does not touch, retract, or reopen D1–D13.

**Numbering note:** the client's own instruction for this change referred to it as "D13 — Google Login." At the time this instruction was received, **D13 was already assigned** to the immediately preceding decision (django-allauth account settings against the stock `User` model, recorded just above). Renaming/renumbering that existing D13 was not an option — "do not reinterpret or rewrite unrelated frozen decisions" forbids it, and it is a real, already-applied decision (SECURITY.md §3, DEPLOYMENT.md §3, DATA_MODEL.md `User`). This entry is therefore recorded as **D14**, the next available number, with this substitution called out explicitly here and in the final report for this task rather than silently resolved.

**Decision:**
- Google Login is added as a client-approved, **additive-only** authentication method (REQ-ACC-04). Local username/password login, signup, and password-reset (REQ-ACC-01) are unchanged and remain fully available — Google is an alternative, not a replacement.
- **Google is the only social provider added.** No GitHub, Facebook, Apple, or Microsoft OAuth is introduced.
- **Stock Django `User` model, unchanged.** No custom `AUTH_USER_MODEL` — django-allauth's own `socialaccount` framework (its `SocialAccount`/`SocialApp`/`SocialToken` tables) links a Google identity to a stock `User` row; no Finance-PSU-designed `GoogleAccount` table was created (DATA_MODEL.md `User`, new note).
- **Implementation:** `django-allauth[socialaccount]` + the Google provider (`allauth.socialaccount.providers.google`), added to `INSTALLED_APPS` — a dependency addition, not yet an actual edit to `requirements.txt` in this pass (that stays untouched per this task's explicit instruction; the pin is documented as the future install target, SECURITY.md §3).
- **Credentials are environment-only:** `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET`, read via `SOCIALACCOUNT_PROVIDERS["google"]["APP"]` from `.env` — never hardcoded, never committed, never a duplicate DB-backed `SocialApp` row carrying production secrets (SECURITY.md §2–§3, DEPLOYMENT.md §3–§4).
- **Identity-only scopes:** `profile` + `email` only — no Gmail/Drive/Contacts/Calendar or any other Google API scope.
- **PKCE enabled** (`OAUTH_PKCE_ENABLED = True`).
- **No offline access, no token persistence:** `access_type: "online"`, `SOCIALACCOUNT_STORE_TOKENS = False` — Finance PSU never requests or stores a Google refresh/access token. This is distinct from the `SocialAccount` relationship row itself, which *is* expected to exist for a Google-authenticated identity (Case B below) — only *token* persistence is disabled.
- **Verified-email-only matching is Google-provider-scoped, not global — corrected this pass (post-D14 Codex review, MEDIUM finding 1).** `SOCIALACCOUNT_PROVIDERS["google"]["EMAIL_AUTHENTICATION"] = True` (not a project-wide `SOCIALACCOUNT_EMAIL_AUTHENTICATION = True`) + `SOCIALACCOUNT_EMAIL_AUTHENTICATION_AUTO_CONNECT = False` — a Google-verified email authenticates into the matching existing local `User` (never creating a duplicate, never leaving a new `SocialAccount` connection on that existing `User`), but only as an explicit login action, never as an implicit background link, and only for Google — no other provider is configured, so none receives this trust automatically if one is added later without a separate decision.
- **Route contract, made explicit this pass (MEDIUM finding 2):** allauth's URLs are mounted via `path("accounts/", include("allauth.urls"))`. With `SOCIALACCOUNT_LOGIN_ON_GET = False`, Google login initiation is a CSRF-protected `POST` to `/accounts/google/login/` (a form/button, not a link) — a bare `GET` does not start the OAuth handshake. The callback, `GET /accounts/google/login/callback/`, is the one URL in this doc set that is not illustrative once configured — it must match the Google Cloud Console redirect URI exactly (API.md §1, DEPLOYMENT.md §4).
- **Unverified-email guarantee, narrowed this pass (MEDIUM finding 3) — previously overstated.** The guarantee is that an unverified Google-asserted email must never authenticate or link to an **existing** Finance PSU account via email matching — the account-takeover-relevant protection. It is not a promise that no pending row can ever be created by stock allauth for an unmatched, unverified identity; `SOCIALACCOUNT_AUTO_SIGNUP` keeps its allauth default and no custom `SocialAccountAdapter` was added solely to forbid that, since it isn't the risk this control exists to close.
- **`SocialAccount` row behavior clarified this pass (LOW finding, TESTING.md):** Case A (existing local `User`, Google-verified-email match) — authenticates the existing `User`, no duplicate, and `AUTO_CONNECT = False` means no new `SocialAccount` connection row persists on it from this login. Case B (brand-new student, first Google signup) — a new stock `User` is created and a `SocialAccount` row recording the Google identity is expected as part of that signup; `SocialToken` persistence still stays disabled in both cases.
- **Single-session rule is universal:** REQ-ACC-02/03's one-active-session enforcement applies identically regardless of which method (local or Google) established the session — no Google-specific session-handling path exists.
- **Finance PSU's own Postgres database remains the system of record** for the account; Google is consulted only at the moment of sign-in to assert a verified identity, never as a store of entitlement, profile, or session state.

**Rationale:** Client-driven scope addition intended to reduce signup friction and improve account portability, without weakening anything already frozen — additive by design, fails closed on every case that actually matters for account takeover (unverified email reaching an *existing* account, provider error, invalid callback state, missing credentials), and introduces no new technology outside `django-allauth`'s own already-approved package (no new infra, no Redis/Celery/microservices, no custom adapter).

**Post-D14 correction (Codex review, this pass — 0 blocker/high, 3 medium, 3 low; documentation-only, no renumbering):** the three medium findings above (global-vs-provider-scoped email trust, the POST/route contract, and the overstated unverified-email guarantee) and three low findings (a stray "§3.7" cross-reference in ARCHITECTURE.md §3.2a corrected to "§3.6"; an abbreviated `SECRET` reference in ARCHITECTURE.md §3.6 corrected to the canonical `GOOGLE_OAUTH_CLIENT_SECRET`; TESTING.md's `SocialAccount` fixture assertions made explicit for the Case A/Case B distinction) are corrected in place, in this same D14 entry and across ARCHITECTURE.md, API.md, SECURITY.md, and TESTING.md — **not** recorded as a new D15, since Codex did not flag the D13/D14 numbering itself as a finding in this review and no unrelated frozen decision needed reopening.

**Status:** Documentation only, applied to REQUIREMENTS.md (REQ-ACC-04, REQ-WEB-07), ARCHITECTURE.md (§3.2a, §3.6, component table), API.md (§1), DATA_MODEL.md (`User` note), SECURITY.md (§2, §3, §10), DEPLOYMENT.md (§3, §4), TESTING.md (15 new integration tests + manual QA items — corrected this pass from a numbering duplicate to 14 named + 1 renumbered, no content loss), and CLAUDE.md (guardrail bullet, below). ## D15 — PDF printing enabled by explicit client decision

**Context:** The `docs-baseline-v2` implementation baseline (REQ-COURSE-03, SECURITY.md §5, D9 item 3, D11.6) blocked printing outright — a `beforeprint` handler intercepting Ctrl+P/menu/`window.print()`, alongside the no-download-button and text-copy deterrence. After that freeze, the client explicitly changed the print policy.

**Decision:**
- **Printing is now enabled.** The PDF reader no longer intercepts or blocks the browser/OS print action in any way — no `beforeprint` handler, no canvas-blanking, no print-dialog suppression.
- **No normal Download control remains** — this part of the prior baseline is unchanged. No download button, no `<a download>`, no direct file link; the PDF is still only ever reachable through the entitlement-checked, presigned-URL flow.
- **Text-copy deterrence remains unchanged** — the PDF.js text layer stays disabled or unselectable, exactly as before. This decision touches printing only.
- **Entitlement, R2 privacy, and the presigned-URL design are entirely unchanged.** Authentication, a non-expired `Enrollment`, and a freshly minted 60-second presigned R2 URL are still required for every chapter open; R2 stays private with no public URL ever generated; Django still never proxies or streams PDF bytes itself (ARCHITECTURE.md §3.4, API.md §3).
- **Accepted limitation:** because printing is enabled, the browser/OS print dialog's own "Save as PDF" destination cannot be reliably prevented — there is no technical control in this stack (short of blocking printing entirely, which the client has explicitly declined) that distinguishes "print to paper" from "print to a PDF file." The client explicitly accepts this as a known residual limitation, not a defect to engineer around.
- **This decision supersedes conflicting print-blocking language** from D9 item 3 and D11.6, and any other prior passage describing printing as blocked or intercepted. D9's and D11's own historical reasoning is left as-is and is not rewritten — the record of what the baseline *was*, and why, stays traceable; this entry records what changed and when.

**Rationale:** Client-driven policy change, made after weighing that reliable print-blocking was never fully achievable against "Save as PDF" in the first place, and deciding the platform is better served by allowing normal printing (a legitimate study-material use case) than by maintaining an interception mechanism that only partially achieves its goal. No new technology, infrastructure, or schema change is introduced — this is a client-side viewer behavior change only.

**Status:** Documentation only, applied to REQUIREMENTS.md (REQ-COURSE-03, §2.1, §5 Out of Scope), SECURITY.md (§5, §10), TESTING.md (§1, §4, manual QA checklist), API.md (§3). ## D16 — 5–10 year maintainability objective

**Context:** The client explicitly confirmed a long-term operational expectation for Finance PSU that hadn't previously been written down as its own principle: the platform should remain maintainable and operable for roughly 5–10 years, not just through the 14-day build and initial handover.

**Decision:**
- **Intended operational lifetime: 5–10 years.** This is an expectation about how the system should be built and operated, not a fixed end-of-life date.
- **Today's exact dependency/framework versions are not frozen for that period.** Supported/LTS software and routine framework/security upgrades are expected over the platform's life — this is a continuation of, not a departure from, the Django 5.2 LTS upgrade-planning note already recorded in DEPLOYMENT.md §9.
- **The simple, conventional architecture already approved is preferred, not replaced.** Django/PostgreSQL/Docker Compose, relational and migration-backed data structures, and minimal unnecessary dependencies remain the standard — favoring long-term maintainability is a reason to keep this architecture simple, not a reason to add speculative infrastructure for anticipated future scale.
- **Deployment should remain reproducible and portable.** The existing Git-and-Docker-Compose deploy process (DEPLOYMENT.md §6) and the stack's stated zero-vendor-lock-in framing (R2's S3-API compatibility, standard Postgres — NFR-03) both already serve this; nothing new is required to satisfy it.
- **Automated regression tests for critical behavior, and restore-tested encrypted backups, are what make upgrades safe.** Both already exist in this doc set (TESTING.md Tier 1, SECURITY.md §8/§10 backup-restore rehearsal) — this decision reinforces their ongoing importance rather than adding new ones.
- **No new infrastructure is introduced because of this principle.** Explicitly: no Redis, no Celery, no Kubernetes, no microservices, no React/DRF rewrite, no Dokploy/Coolify/1Panel or other management panel dependency. A management panel may be considered later as optional operational tooling, but Finance PSU must never depend on one to function (ARCHITECTURE.md §4).

**Rationale:** A long operational horizon is best served by keeping the system boring, conventional, and well-tested rather than by pre-building for scale or flexibility it doesn't yet need — consistent with this project's existing "Simplicity First" stance (CLAUDE.md) and the approved stack's own zero-vendor-lock-in framing. Recording it as an explicit principle here means future maintenance work has a stated client expectation to work against, rather than an implicit assumption.

**Status:** Documentation only, applied to REQUIREMENTS.md (NFR-07, §2.1), ARCHITECTURE.md (§4), DEPLOYMENT.md (§9). No schema change — DATA_MODEL.md's 16 models are unaffected. No application code, migrations, or tests were changed in this pass.
